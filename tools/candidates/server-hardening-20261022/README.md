# 専用サーバー防御層（2026-10-22）

既存のアプリケーションを変更せず、元の Worker を import する追加層。現在は候補のみで、本番・確認版には適用していない。

- OAuth の POST コールバックだけを実測16KiB・10秒で制限する。通常の学習保存の本文にはこの制限を適用しない。
- 専用 Durable Object で要求数を直列管理する。通常要求は毎秒120・認証入口は初期20回と毎分20回相当。IP はアクセス権や本人確認には使わない。
- 防御用保存先が使えない場合は503、過剰要求は429と再試行秒数を返す。認証・所有者確認・学習保存は元の Worker に委ねる。
- PDF の埋め込み、マイク、Cookie、OAuth リダイレクト等を維持し、nosniff・referrer・HTTPS の HSTS ヘッダーを追加する。

`main-entry.mjs` は手元の大型更新、`public-entry.mjs` は既存の公開版用ソースをそれぞれ参照する。両者を混ぜない。`main-worker.js` と `public-worker.js` は旧案の記録であり、適用禁止。

検証は全体検証の終了と全成功を待ち、`python3 tools/candidates/server-hardening-20261022/verify-layer.py` を単独実行する。実行器も、自分の全体成功の終了記録とログSHAがなければ機能検証へ進まない。合成要求と外部通信を遮断したローカル workerd を使い、実ユーザーの認証・成績・秘密値には触れない。実行結果は `verification.json`、失敗時は `checks/` に保存する。未実行を成功扱いにしない。

本番への適用には、専用 binding と新クラスの migration を別の公開設定へ追加し、dry-run と契約上の公開前検証を行う必要がある。既存設定の変更や公開はまだ実施していない。既存 OAuth の本人確認・Google/LINE の実機確認も別途必要。

この層だけで侵入を完全に防げるとは扱わない。大量の異なるIPからの攻撃、帯域攻撃、DO呼び出し費用の抑制には Cloudflare 側の WAF・DDoS・レート制限の設定確認が別途必要で、現在のアカウント設定は読み出していない。共有ネットワークで認証制限が強すぎないかも、適用前に確認する。

防御層の点検・記録後は、元の協力RPG等の作業へ戻る。完了済みの教材制作・不変の検証を重複実行せず、変更のある範囲を優先する。
